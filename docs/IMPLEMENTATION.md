# 박스오피스 대시보드 실제 구현 계획

상태: 실행 계획 기록 — F1 demo·KOBIS 연동 완료, B단계 Supabase SQL·코드 작성 완료, 실제 DB 통합 검증 대기

기준: [PRD](../PRD.md) · [아키텍처](../ARCHITECTURE.md) · [작업 지침](../AGENTS.md) · [ERD](../ERD.md) · [단계 계획](../PLAN.md)

이 문서는 실제 KOBIS·DB 연동을 위한 실행 설계다. 제품 동작과 합격 여부는 PRD의 AC, 저장 형태는 후속 ERD의 `movies`·`box_office_periods`·`box_office_results` 세 테이블을 따른다. ARCHITECTURE의 단일 JSONB 캐시 절은 대체 대상이며 함께 구현하지 않는다. 아래 단계는 PLAN의 Phase 승인 절차를 바꾸지 않는다.

## 1. 화면 상태

| 상태 | 판단 기준 | F1 목록 | F2 인사이트 |
| --- | --- | --- | --- |
| 로딩 | 현재 조건의 응답을 기다리는 중 | 로딩 안내, 이전 조건의 표 숨김 | 로딩 안내, 이전 조건의 확정 지표 숨김 |
| 성공 | 유효한 응답에 원본 영화 1편 이상 / 분석할 유효 일간 데이터 있음 | 실제 기간·갱신 시각·여섯 열 표시 | 추이·Top·총합·점유율·조회 목록 기준 안내 표시 |
| 정상 빈 결과 | 성공 응답의 원본 목록이 `[]` / 분석 기간 전체가 정상 빈 날짜 | 데이터 없음 안내. 검색어가 있어도 이 상태 우선 | 가상 0 지표 없이 기간 데이터 없음 안내 |
| 검색 결과 없음 | F1 원본 목록은 있으나 현재 영화명 필터 결과가 `[]` | 전용 안내와 검색 초기화 | 해당 없음. F1 검색어는 F2에 적용하지 않음 |
| 일부 날짜 없음 | F2 기간의 일부 날짜가 정상 빈 응답 | 해당 없음 | 해당 날짜 차트 공백, 누락 안내와 유효 날짜 수. 존재하는 날짜만 집계 |
| 오류 | 네트워크·외부 API·DB 조회·응답 검증 실패 또는 제한 시간 초과 | 오류 안내, 현재 조건 재시도 | 한 날짜라도 오류면 확정 Top·총합 중단, 오류와 재시도 |
| 입력 오류 | 잘못된 달력 날짜·미래 날짜·허용되지 않은 선택값 | 입력 안내, 요청 차단 | 같은 원칙으로 요청 차단 |

조건이 바뀌면 이전 요청을 취소하거나 응답 키를 대조해 늦게 온 결과를 버린다. 정상 빈 결과는 오류나 매출·관객수 0과 다르다. 검색 결과 없음은 서버의 빈 응답 상태가 아니라 브라우저 필터 상태다.

## 2. 책임 경계

| 계층 | 책임 | 맡지 않는 일 |
| --- | --- | --- |
| 화면(브라우저) | 날짜·기간·검색어·F2 기간·Top 선택, 기본 날짜를 한국 시간 전날로 설정, 즉시 입력 검사, 내부 API 호출, 상태별 안내, 정확한 정수 포맷, F1 현재 목록 검색, 검증된 일간 응답의 F2 집계와 진행률 표시 | KOBIS/DB 직접 호출, 비밀키 사용, 원본 수치의 신뢰성 판단 |
| 서버(Next.js Route Handler·서비스) | 요청 재검증, 캐시 유효성 판단, KOBIS 어댑터·시간 제한·요청 제한·중복 갱신 조정, 응답 구조·숫자 검증, `bigint` 정규화, DB 트랜잭션, 저장본 대조, 안전한 HTTP 응답 | 비밀값·외부 오류 원문 공개, 실패를 빈 결과로 변환, 만료 캐시를 최신으로 반환 |
| DB(Supabase Postgres) | 영화·조회 기간·실적 저장, PK/FK·유일성·인덱스·원자적 교체, 조회 시각·TTL, 기간별 동시 저장 직렬화 | 브라우저의 테이블 직접 조회, 외부 API 호출, 화면 검색어별 별도 캐시 |

`KOBIS_API_KEY`와 `SUPABASE_SECRET_KEY`의 실제 값은 로컬에서 `.env.local`에만 두고 서버 모듈에서만 읽는다. 브라우저 번들·응답·로그에 노출하지 않는다. 배포 환경 주입 방식은 배포 전에 별도로 확정한다.

## 3. 내부 API 계약

현재 F2 계약: **`GET /api/box-office?date=YYYY-MM-DD&type=daily`**를 종료일 포함 7/14/30개 날짜에 각각 요청한다. 화면은 최대 3개를 동시에 조회하고 날짜별 상태·진행률을 표시한다. 기존에 계획한 `GET /api/insights?endDate=YYYY-MM-DD&days=7|14|30&top=5|10`은 현재 구현되지 않았으며 아래 표의 해당 행은 초기 설계 기록이다.

| API | 요청 파라미터 | `200` 성공 응답의 `data` | `200` 성공 응답의 `meta` |
| --- | --- | --- | --- |
| `/api/box-office` | `date` 필수, 유효한 과거/오늘 달력 날짜; `type` 필수, `daily`·`weekly`·`weekend` | `status: "data" \| "empty"`, `items: [{ movieCd, movieNm, rank, openDt, salesAmt, audiCnt, salesAcc, audiAcc }]`; 빈 응답은 `items: []` | `date`, `type`, `rangeStart`, `rangeEnd`, `fetchedAt`, `expiresAt`, `source: "cache" \| "kobis" \| "fixture"`, `cachePersisted: boolean` |
| `/api/insights` | `endDate` 필수, 유효한 과거/오늘 날짜; `days`는 `7`·`14`·`30`; `top`은 `5`·`10` | `status: "data" \| "empty"`, `trend: [{ date, status: "data" \| "empty", salesAmt, audiCnt }]`, `topMovies: [{ movieCd, movieNm, salesAmt, audiCnt }]`, `totalSales`, `totalAudience`, `leaderSalesShare`; 정상 빈 날짜의 매출·관객은 `null`, 전체가 비면 확정 지표는 `null` | `startDate`, `endDate`, `days`, `top`, `validDateCount`, `emptyDateCount`, `oldestFetchedAt`, `newestFetchedAt`, `dailyFetchedAt`; 날짜별 출처·저장 상태도 포함 |

공통 응답은 `{ "data": ..., "meta": ... }` 형태다. `rank`와 날짜별 개수는 안전한 정수, 금액·관객수와 합계는 검증된 **십진 문자열**로 직렬화한다. `openDt`는 날짜 또는 `null`; 점유율은 소수점 한 자리로 계산해 문자열(예: `"12.3"`)로 반환하고 분모 0이면 `null`이다. `trend`의 정상 빈 날짜는 차트 공백으로 그린다. F2는 `salesAmt`·`audiCnt`만 합산하고 `salesAcc`·`audiAcc`를 더하지 않는다. F2 검색어나 F1의 주간·주말 선택은 이 API 입력에 포함되지 않는다. 데모의 `source`는 `fixture`, `cachePersisted`는 `false`, DB 시각인 `fetchedAt`·`expiresAt`은 `null`이다. 라이브에서 DB 저장 실패 후 검증된 결과를 반환할 때도 `cachePersisted=false`, `expiresAt=null`로 표시한다.

실패 응답은 `{ "error": { "code": "...", "message": "사용자용 안전한 문구" } }`로 통일하고 `data`와 확정 인사이트 지표를 포함하지 않는다. 요청 ID를 사용한다면 비밀값 없는 `meta.requestId`만 추가한다.

| HTTP 코드 | 상황 | 화면·서버 처리 |
| --- | --- | --- |
| `400` | 날짜·기간·`days`·`top` 값 오류, 미래 날짜 | 입력 안내. KOBIS·DB 조회 전 차단 |
| `429` | 내부 요청 제한 초과 | 잠시 후 수동 재시도 안내. 자동 무한 재시도 금지 |
| `502` | KOBIS 네트워크/외부 오류, 응답 구조·필수 값 검증 실패 | 오류 안내·재시도. 빈 결과 또는 성공 캐시로 저장하지 않음 |
| `504` | KOBIS 5초 또는 F2 전체 20초 예산 초과 | 시간 초과 안내·재시도. 부분 집계 반환 금지 |
| `503` | DB 조회 실패, 갱신 임대 대기 시간 초과, 필수 서버 설정 누락, 저장 후 대조 실패 | 오류 안내·재시도. 만료 데이터 반환 금지 |

정상 빈 응답은 `200`이며 실패 코드가 아니다. 현재 데모 API의 `{status, items, ...}`와 `{status:"error", code, message}`는 이 최종 계약과 다르므로 화면·테스트를 함께 이행한다. 이행 중 `DATA_MODE=demo`는 fixture만, `live`는 실제 서비스만 사용하고 실패 시 다른 모드로 자동 전환하지 않는다. `demoScenario`는 데모 전용이며 실제 API 계약에 포함하지 않는다.

## 4. 요청 처리와 실패 정책

**입력 검증 → 캐시 조회 → 외부 호출 → 저장 → 저장본 대조 → 응답**. 유효한 캐시가 있으면 외부 호출·저장·대조를 건너뛰고 저장본을 응답한다. F2의 날짜별 진행률·실패 날짜만 재시도 요구에 따라 화면이 `/api/box-office`를 날짜별로 요청한다. 각 응답은 기존 서버 검증·캐시 경로를 거치며, 화면은 성공한 일간 응답만 `bigint`로 집계한다. 한 날짜라도 실패하면 확정 기간 합계·Top을 숨긴다.

| 단계 | 정상 동작 | 실패하면 |
| --- | --- | --- |
| 1. 입력 검증 | 화면과 서버에서 날짜·열거값 검사. KOBIS `targetDt`와 주간/주말 매핑은 공식 계약 확인 후 확정 | `400`; 외부 호출·DB 쓰기 없음 |
| 2. 캐시 조회 | 기간 유형·기준일·조회 범위(초기 10편, 전체)로 키 조회. `expires_at > now`인 `data`/`empty`만 사용. 읽기로 TTL 연장하지 않음 | DB 조회 오류 `503`; 만료 또는 미존재면 갱신. 한 서버 프로세스 안의 같은 키 요청은 진행 중인 갱신을 공유 |
| 3. 외부 호출·검증 | 일간/주간·주말 KOBIS 호출, 실제 `showRange`·필수 구조·숫자 문자열 검사. `movieCd`로 식별하고 `bigint`로 계산 | 외부/검증 오류 `502`, 시간 초과 `504`; 기존 정상 저장본·TTL 유지, 만료값은 최신으로 반환하지 않음 |
| 4. 저장 | 한 트랜잭션에서 영화 upsert, 기간 메타데이터 갱신, 해당 기간 실적 전체 교체. 정상 빈 결과는 기간 행과 실적 0행 저장. 기간별 advisory lock·시각 비교로 늦은 갱신 쓰기 차단 | 롤백하고 기존 정상 저장본 유지. ARCHITECTURE 정책대로 검증된 외부 결과는 `200`, `meta.cachePersisted=false`로 반환할 수 있으나 캐시 적중을 보장하지 않음. 비밀값 없는 저장 실패 기록 |
| 5. 저장본 대조 | **저장에 성공한 경우에만** 기간·상태·행 수·영화 코드별 필드·`fetchedAt`/`expiresAt`을 재조회해 검증된 외부 결과와 비교. 동일 갱신 버전/시각을 확인해 다른 갱신과 혼동하지 않음 | DB 재조회 오류 또는 불일치는 `503`; 해당 버전의 캐시를 무효화하거나 재사용을 차단한 뒤 운영 조사 대상으로 기록. 사용자에게 안전한 재시도 안내 |

데이터 TTL은 **24시간**, 정상 빈 응답 TTL은 **1시간**이다. 이는 프로젝트 정책이지 KOBIS의 갱신 보장이 아니다. KOBIS 요청당 제한 시간은 **5초**, F2 전체 요청 예산은 **20초**, 날짜별 동시 외부 요청은 최대 3개를 목표로 한다. B단계에서 같은 키 저장은 DB advisory lock과 요청 시각 비교로 보호한다. 서버 인스턴스 간 중복 외부 호출과 요청 수 제한은 미구현이므로 배포 전에 보강·검증한다. 읽기·쓰기 및 저장본 대조가 여러 쿼리로 나뉘면 동일 갱신 시각을 확인해 경쟁 상태를 감지한다.

## 5. 구현 우선순위와 완료 확인

기존 [PLAN](../PLAN.md)의 Phase 경계와 승인 절차를 따른다. 아래는 **승인된 Phase 안에서의 개발 순서**이며 다음 Phase를 자동 시작한다는 뜻이 아니다.

| 우선순위·순서 | 구현할 것 | 단계 완료 확인 기준 |
| --- | --- | --- |
| P0 · 1. 설계 정합성 | ARCHITECTURE의 JSONB 저장 절을 ERD 세 테이블과 맞추고 API `data/meta` 계약·데모 이행 방식을 확정 | 저장 방식이 하나로 정리되고 계약 예시가 화면·서버·테스트에 동일하게 사용됨 |
| P0 · 2. KOBIS 계약·어댑터 | 공식 일간/주간·주말 파라미터·기간·오류 형식 확인, 입력·숫자·응답 검증, 서버 전용 호출 | 세 유형 fixture와 실제 연동 확인이 구분돼 통과. 잘못된 값·정상 빈·외부 오류가 분리되고 큰 정수 정밀도 유지 |
| P0 · 3. DB·캐시 | 세 테이블, 권한, 트랜잭션 교체, TTL, 동시 갱신·요청 제한, 저장본 대조 | 격리된 테스트 DB에서 JOIN·FK·중복·롤백·`data→empty`·저장/재조회 대조 통과; 캐시 적중 때 외부 호출 없음 |
| P0 · 4. 실제 F1 | `live` 목록 API·화면, 전날 기본 날짜, 실제 기간·갱신 시각, 검색·상태·재시도 | PRD AC 1~5·13·14의 F1 시나리오가 실제 데이터 경로에서 통과. 조건 변경 시 오래된 결과 없음 |
| P0 · 5. F2 | 일간 7/14/30일 API·차트·Top 5/10·보조 지표·결측/오류 처리 | PRD AC 6~12 통과, ERD의 3일 설명용 데이터로 총매출 810,000,000원·총관객 81,000명 독립 대조 |
| P0 · 6. 통합·배포 준비 | AC 1~17, 비밀키 경계, 30일 성능·복구, 공식 무료 요금제·KOBIS 제한 확인 | 필수 검사에 실패·미실행 없음. 확인일·출처·예상 사용량 기록과 배포 승인 후 URL 운영 점검 완료 |

KOBIS 계약·테이블 저장·지표 계산을 바꾸는 단계에는 `box-office-verification` Skill의 **통과/실패/미실행** 보고를 적용한다. 모의 fixture 통과를 실제 외부 호출이나 테스트 DB 검증 통과로 대체하지 않는다. 각 Phase 종료 시 PLAN의 완료 기준별 결과를 보고하고 다음 Phase 승인을 기다린다.

## 6. 1부 데모와의 차이
